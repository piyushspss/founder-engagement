# Founder Engagement Workflow

A **human-in-the-loop Founder Engagement Workflow for the (-1→0) funnel** that turns messy founder
records into explainable evidence, prioritizes reviewer attention, supports human disposition and
workflow decisions, and prevents potentially interesting founders from silently falling through the
cracks.

It replaces the LinkedIn → Excel → ATS → manual-review → spreadsheet loop with one operating
system: import + normalize → assess → priority work queue → human decision → stage workflow →
keep-warm resurfacing → weekly dashboard.

**[`docs/PLAN.md`](docs/PLAN.md) (v2.3, FROZEN) is the source of truth** for scope, assessment
model, safety policy and architecture.

> The product is designed around Redesign's asymmetric cost: **missing an exceptional founder is
> worse than reviewing an extra candidate.** Uncertainty and exceptional evidence bias toward human
> review, never toward rejection.

## Architecture

```text
JSON / CSV
    ↓
Normalizer
    ↓
Dedup + Data Quality
    ↓
Evidence Engine
    ↓
Deterministic Assessment
    ↓
Safety Policy
    ↓
Priority Queue
    ↓
Human Decision + Workflow
    ↓
Nurturing / Keep Warm / Resurface / Deal

Optional:
Normalized supplied facts
    ↓
Constrained LLM evidence check
    ↓
Provenance validation
    ↓
Raise-only ephemeral attention overlay
```

Serving shape: React + Vite + Tailwind UI → FastAPI → SQLAlchemy → SQLite. `assessment/`, `evidence/`
and `policy/` are pure functions over a `CanonicalProfile`, unit-tested independently of the API.

### The authority boundary

This is the single most important design decision in the system.

| Layer | May produce | May never produce |
|---|---|---|
| **Deterministic system** | evidence, `potential`, `confidence`, `attention`, `data_state`, archetype, `recommended_action` | a disposition, a lifecycle stage |
| **Optional AI layer** | additional *contextual* evidence; may only **raise** attention | any deterministic field, any score, any disposition, any stage — and it cannot lower attention |
| **Humans** | `decision` (disposition), `stage`, `owner`, `next_action`, `notes` | — |

The machine prioritizes **attention** and **recommends**. Humans alone set disposition and lifecycle
stage. The AI layer's authority is deliberately the narrowest of the three, because it is the layer
whose output we can currently validate the least.

> **Recommended posture after real-provider evaluation: the optional LLM layer is a contextual
> second set of eyes over supplied founder facts, and its output is display-only.** Real-provider
> evaluation found promising contextual observations but **not** sufficient evidence to let the LLM
> change Review Priority, so the "may only raise attention" capability above — which exists in the
> code and is what the evaluation tested — should stay unused until human reviewer labels justify
> it. Deterministic assessment remains the prioritization authority.
> Full evidence: [`docs/EVAL_REPORT_REAL_PROVIDER.md`](docs/EVAL_REPORT_REAL_PROVIDER.md) ·
> [`docs/CP10_1_PRESERVED.md`](docs/CP10_1_PRESERVED.md) ·
> [`docs/CP10_2_DESIGN.md`](docs/CP10_2_DESIGN.md) ·
> frozen manifest [`docs/cp10_2_experiment_manifest.json`](docs/cp10_2_experiment_manifest.json) ·
> audit evidence [`docs/cp10_2_holdout_raw.jsonl`](docs/cp10_2_holdout_raw.jsonl).
>
> **Rules prioritize. AI notices. Humans interpret.**

### Optional AI environment setup

Three providers sit behind one adapter interface. `LLM_PROVIDER` selects one:

| `LLM_PROVIDER` | adapter | needs |
|---|---|---|
| `mock` | `MockAdapter` | nothing — deterministic, finds nothing by default |
| `openai` | `OpenAIAdapter` | `OPENAI_API_KEY` + `pip install -r backend/requirements-openai.txt` |
| `anthropic` | `AnthropicAdapter` | `ANTHROPIC_API_KEY` + `pip install -r backend/requirements-llm.txt` |

Secrets go in a local **`.env`, which is gitignored** — copy the committed
placeholder template and edit it:

```bash
cp .env.example .env      # then edit .env; never commit it
make env-check            # prints provider + availability, never a key value
```

`make api` and `make ai-openai` source `.env` if it exists. Exporting the variables in your shell
works identically — nothing in the app reads a file directly, only the environment.

```bash
pip install -r backend/requirements-openai.txt
python scripts/openai_eval.py --dry-run           # plan + budgets, no network request
```

Real-provider runs are **cost-guarded in code**, not by operator discipline. The initial authorized
experiment is **5 paid calls, ceiling $0.10 estimated**: `BudgetedAdapter` counts every provider
attempt *before* delegating and refuses the next one at either ceiling. SDK auto-retries are
disabled, so one attempt is one billed request and a retry cannot slip past the counter. There is
deliberately no command that runs the wider 16-profile sample — it needs two explicit flags and a
raised `--max-calls`.

With no key, `GET /config → ai_layer` reports `available: false` with
`detail: "OPENAI_API_KEY is not set"` (or the Anthropic equivalent), and
`POST /founders/{id}/ai_check` returns `status: "unavailable"` and changes nothing. It **never
silently substitutes the mock**, and the UI labels the three states differently: *AI evidence check
unavailable* / *Mock AI evidence check* / *Run AI evidence check*.

Switching provider changes no deterministic number: provider selection is a deployment detail and
enters no rubric section, no `rubric_version` and no rescore semantics. An unrecognised
`LLM_PROVIDER` **fails closed** with `UNKNOWN_LLM_PROVIDER` rather than silently selecting another
vendor — a typo must not spend money at, or send founder data to, a provider nobody named.

## The five capabilities

1. **Import + normalization** — JSON/CSV → canonical profile, conservative dedup, data-quality
   flags, provenance on every field.
2. **Explainable assessment** — Review Priority (0–100), potential, evidence confidence, archetype,
   exceptional signals, missing/contradictory data. Every signal carries its source fields and
   whether it is `OBSERVED`, `DERIVED` or `AI_INTERPRETED`.
3. **Safety policy / attention prioritization** — ordered, unit-tested rules and guards
   (PLAN §4.5). Uncertainty raises review; missing data is never negative evidence.
4. **Human engagement workflow** — disposition, stage machine, owner, next action, notes,
   keep-warm 3/6/9 months, re-engagement resurfacing, full audit trail.
5. **Operating dashboard** — stage counts, weekly intake, ageing, stuck, re-engagement due,
   review-queue size, low-confidence share, human decisions recorded.

## API

```
POST   /import                          JSON or CSV -> normalize -> dedup -> assess -> store
POST   /rescore                         re-run the pipeline under the effective config
GET    /config    PUT /config           read / change the effective rubric (PUT never rescores)
GET    /queue                           filters: attention, data_state, stage, owner, due, as_of
GET    /founders/{id}                   facts | assessment | metadata | decision | workflow | dups
GET    /dashboard                       stage counts, weekly intake, ageing, stuck, due, low-conf %
GET    /audit/{id}                      who changed what, when, why
POST   /founders/{id}/ai_check          OPTIONAL, explicit, human-initiated; never automatic
POST   /founders/{id}/decision          HUMAN — disposition + actor + reason
POST   /founders/{id}/stage             HUMAN — validated transition; KEEP_WARM needs months 3/6/9
POST   /founders/{id}/notes             HUMAN — append-only
PATCH  /founders/{id}/workflow          HUMAN — owner / next_action only
```

The four HUMAN routes are the only code paths that write `decisions` or `workflow`. Import,
assessment, rescore, config changes and AI checks never create or alter a human decision or a stage;
a newly imported founder has **no** human decision and sits at the neutral `NEW` creation default,
which is not a machine recommendation.

**Stage transition map** (conservative where the frozen plan is silent — no backward edges were
invented, `CLOSED` is terminal and reachable from every non-terminal stage):

```
NEW -> ASSESSMENT, CLOSED   ·   ASSESSMENT -> POTENTIAL, NURTURING, CLOSED
POTENTIAL -> NURTURING, KEEP_WARM, DEAL, CLOSED   ·   NURTURING -> KEEP_WARM, DEAL, CLOSED
KEEP_WARM -> NURTURING, DEAL, CLOSED   ·   DEAL -> CLOSED   ·   CLOSED -> (terminal)
```

**Config.** `PUT /config` writes a persisted *runtime* config initialised from `backend/config/*`;
the frozen files are never rewritten. Objects deep-merge, lists are replaced wholesale. A config
change alters what the *next* assessment uses — `POST /rescore` is the explicit act that
re-evaluates founders, and it re-runs from stored **raw** because tier lists change normalization,
not merely scoring. **A rescore cannot mutate a human decision or a workflow stage**; it reports
`human_state_touched: false` and is proved by `test_rescore_integrity.py`.

**Versioning.** `rubric_version` is the SHA-256 of the complete effective config (the four rubric
sections and nothing else — no timestamps). `assessment_version` starts at 1 and increments on every
successful reassessment; a failed reassessment increments nothing, because the whole rescore is one
transaction.

**CSV import contract.** One row per founder; column names are raw-schema field names; `experience`,
`education` and `professional_emails_hashed` cells carry JSON; empty cells mean absent, never empty
string.

## Optional AI evidence layer

An **overlay**, never a replacement. The deterministic assessment is the source of truth; the AI
layer reads it, never writes it, and can only ever **raise** attention
(`ROUTINE → REVIEW → PRIORITY_REVIEW`; the reverse is impossible by construction and tested
exhaustively). Its result is returned by the endpoint and **not persisted** — no AI column, no AI
field inside `Assessment`, no audit event, no `RESCORE` event.

Nothing calls it for you: not import, not the queue, not rescore, not the dashboard, not the founder
GET. Cost, latency and human intent all stay visible.

* **Adapters** — `MockAdapter` (deterministic, `provider="mock"`, finds nothing by default),
  `AnthropicAdapter` (`claude-opus-5`) and `OpenAIAdapter` (`gpt-5-mini` by default, overridable
  with `OPENAI_MODEL`). Both real SDKs are imported lazily, and all three normalise to the same
  internal result contract, so grounding, safety policy, the raise-only overlay and the persistence
  boundary are identical whichever provider is configured. Provider-side structured output does
  **not** replace application validation — every response is re-validated here regardless.
* **Data minimisation** — every identity hash (email, LinkedIn, phone, github, crunchbase, name,
  `mdm_person_id`) is withheld. No web search, no enrichment, no outside knowledge.
* **Prompt-injection boundary** — profile strings are DATA. The system prompt says so by field name,
  and an instruction inside a headline still cannot ground a claim, because the whitelist has no
  path for it.
* **Provenance whitelist (hard gate)** — every `source_fields[]` path must exist on *this* founder
  and hold a value. A path that does not is **discarded, never repaired to a nearby one**;
  cross-profile citations are reported by name.
* **Unsupported inferences** are diagnostic only — never a Signal, never a score, never presented as
  established evidence.
* **Aggregation** reuses the frozen exceptional rule: one STRONG cue, or two MEDIUM cues, justifies a
  PRIORITY_REVIEW floor; a single MEDIUM cue is shown as an unusual-evidence cue without claiming
  the override fired.
* **Frozen prompt** — `prompt_version cp10.1`, SHA-256
  `50e3a4ef68af10dd161c1282cedc6401e5f79b73430a1a26d188ed1b880b3a76`, recorded in
  [`docs/EVAL_DECISIONS.md`](docs/EVAL_DECISIONS.md)
  **before** the first golden-set batch and asserted by test. It was never tuned against golden
  outcomes.
* **`GET /config → ai_layer`** exposes read-only **status** information — provider availability and
  prompt version/hash — so the UI can label the optional action honestly before a person spends a
  call on it. It is **status only**: it does not enter the scoring rubric or the rubric hash (F-24).

## Keep-warm resurfacing

A founder is **re-engagement due** exactly when `stage == KEEP_WARM` and
`keep_warm_until <= as_of`. Both sides are dates, the comparison is inclusive, and no local clock or
browser timezone takes part — the product dates everything from UTC.

`?as_of=YYYY-MM-DD` on `/queue`, `/dashboard` and `/founders/{id}` is a **read-time lens**. It
changes what a person is shown and writes nothing: no row, no stage, no assessment, no audit entry.
An unparseable date is rejected with 422 rather than silently treated as today.
`scripts/simulate_time.py` demonstrates it and proves the purity by hashing every table before and
after.

A due date arriving is a **human commitment coming round, not the model changing its mind**, so
`why_surfaced` carries machine reasons and `workflow_reasons` carries `Re-engagement due`. A founder
can read *machine attention: Routine* and *workflow: Re-engagement due* at once; that is not a
contradiction.

**Re-engage** is the human act: `POST /founders/{id}/stage` with `NURTURING`, actor and reason. It
moves the stage, clears the obsolete keep-warm date, audits both, and preserves the disposition,
owner, next action, notes and the entire machine assessment. *Re-engage early* is offered too, and
early founders never count toward the due KPI.

**Stuck** is `> N days` in the current stage, N defaulting to 14 and overridable per request with
`?stuck_days=`. It excludes `KEEP_WARM` (waiting is the commitment), `CLOSED` and `DEAL`.
`stuck_days` is an operational display threshold and never enters `rubric_version`.

## UI

Three screens, React + Vite + Tailwind, hash-routed, no state library.

* **S1 Priority Queue** (home) — KPI strip from `/dashboard`; table ordered exactly as the API
  returns it (attention → evidence confidence → id). **Potential is never the ranking key.** Every
  filter is a server-side query parameter.
* **S2 Founder Detail** — machine assessment, "why this assessment?" (policy trace + signal table
  with weight, value, weighted contribution, strength, provenance type and source fields),
  exceptional evidence, archetype, missing/contradictions/duplicates, normalized timeline, then a
  visually separate **Human decision** panel and the audit history.
* **S3 Pipeline & Dashboard** — Kanban by stage with explicit, reason-carrying moves; weekly
  metrics; a config drawer for weights, thresholds, tier lists and the health taxonomy.

Presentation rules the UI is tested against (`frontend/src/screens/parts/boundary.test.tsx`):

* `UNKNOWN` is an **unmade judgment**, never a worse `LOW`. Different chip, different copy
  ("insufficient evidence to judge" vs "sufficient evidence, limited positive signals"), never red,
  never ranked below `LOW` on a quality scale (F-9).
* A **detector cue** ("Exceptional progression — Medium") is shown separately from the
  **aggregated** state ("Priority override triggered: Yes/No") (F-13).
* The four dimensions are four visually different things — pill, outlined chip, meter, square tag —
  so `Priority Review + Unknown` reads as a sentence, not a contradiction.
* There is **no "accept the recommendation" shortcut**. Disposition and stage are separate human
  acts with separate reasons and separate API calls.
* Saving configuration never rescores. A founder whose stored `rubric_version` differs from the
  effective one shows **"Assessment needs recalculation"**.

Full detail in [`docs/EVAL_REPORT.md`](docs/EVAL_REPORT.md); methodology and every adjudicated

| metric | value |
|---|---|
| golden cases | 50 (15 must-surface · 15 reasonable-low · 10 ambiguous/spiky · 10 data-quality/adversarial) |
| must-surface recall | **1.000** (15/15) |
| must-surface leakage into ROUTINE (hard property, must be 0) | **0** |
| expectation pass rate (all four dimensions + evidence assertions) | **100%** (50/50) |
| review-queue rate | 62.0% (31/50) |

> designed sparse/contradictory scenarios. It is not an estimate of real-world accuracy at
> identifying great founders.** Real validation requires reviewer-labelled historical candidates
> and/or prospective reviewer feedback.

> The no-op MockAdapter result proves only that the AI subsystem does not alter deterministic
> behavior. It is **not** evidence that an LLM improves founder discovery, and no such improvement
> has been demonstrated.

**Real-provider LLM evaluation (post-CP11, OpenAI `gpt-5-mini`)** — full report:
[`docs/EVAL_REPORT_REAL_PROVIDER.md`](docs/EVAL_REPORT_REAL_PROVIDER.md)

| | cp10.1 (discovery, n=5) | cp10.2 (frozen holdout, n=30) |
|---|---|---|
| safety / persistence / no-lowering | held | held (all 7 counters 0) |
| controls un-escalated | — | 13/13 (10/10 of the parsable responses; 3 malformed failed closed) |
| useful contextual observations | 0 net new surfaces | 4/10 headroom cases (gate ≥3: PASS) |
| justified escalations | — | **0** (gate ≥2: **FAIL**) |

> **Rules prioritize. AI notices. Humans interpret.** The deterministic system remains the authority
> for founder prioritization. The LLM showed promising value as a contextual second set of eyes but
> did **not** demonstrate enough evidence to automatically change Review Priority. Recommended

> LLM-driven attention escalation stays **not enabled** until validated with real human reviewer

## Known limitations

1. **No real outcome-labelled training or evaluation data exists.** Nothing in this repository has
   been validated against founders who actually succeeded or failed.
2. **Golden-set metrics are policy-consistency metrics, not founder-success accuracy.** "Recall
   1.000" means 15/15 designed must-surface scenarios obeyed the intended policy — not that 100% of
   real great founders will be found.
3. **Automated LLM-driven attention escalation did not pass its frozen gates and is not
   recommended.** The cp10.2 holdout produced 0 justified and 1 false-positive escalation. The layer
   earned a display-only role, nothing more. Note the code *does* still contain the bounded
   one-level escalation capability — that is what the holdout tested — so "not enabled" is a
   deployment recommendation, not a statement about the implementation.
3b. **Real-provider evidence is thin and one-sided.** 35 real calls total, one provider, one model
   snapshot, on synthetic golden profiles; **3/30 holdout responses were malformed** (the model
   returned 13–14 `source_fields` against a 12-item contract — failed closed, but an
   integration-contract reliability issue to fix before production). Utility classifications are
   provisional AI-assisted analysis, not human ground truth, and useful contextual observations may
   be **positive, negative or ambiguous** — usefulness is not directionality. No claim of improved
   recall, improved ranking or production readiness is made.
4. **AI provenance validation proves source-path validity, not full semantic entailment.** It
   verifies a cited path exists and holds a value, and fails closed when a quoted literal is absent
   from the cited values; it cannot establish that an arbitrary unquoted paraphrase is true (F-23).
5. **Real-provider model outputs are not treated as bit-for-bit reproducible evaluation
   fixtures**, for any provider. The MockAdapter is the deterministic gate. The specific reason
   differs by provider and only the observed one is claimed: **F-22 is Anthropic-specific** —
   `temperature`, `top_p` and `top_k` are rejected by current Claude models, so there is no
   sampling knob to pin. That finding has **not** been observed against OpenAI and is not asserted
   of it; the OpenAI adapter simply sends no sampling parameter and makes no determinism claim.
6. **`(0→1)` idea/company evaluation is not built.** Scope is the person, in the `(-1→0)` funnel.
7. **No LinkedIn / Crunchbase / GitHub enrichment.** Confidence is limited by whatever the source
   record happens to contain.
8. **No email / calendar / Slack / CRM integrations.** Disposition and stage live here; outreach
   does not.
9. **Local, single-tenant demo.** One process, one SQLite file, one user's machine.
10. **No auth and no RBAC.** The "Acting as" field in the header is the audited actor, on trust.
11. **SQLite is an MVP tradeoff, not a production concurrency architecture.** Fine at ≤1000/week
    and a single writer; not a multi-user story.
12. **Starter institution/company tier lists and scoring weights are assumptions requiring business
    calibration.** They are Redesign-plausible, not Redesign's real lists. They are config, not
    code, and editable in the UI.
13. **The deliberate recall-first policy increases false positives and reviewer load.** On the
    seeded 800-founder population 787 founders (98%) sit at REVIEW or above; on the golden set the
    queue rate is 62% at baseline and 98.4% under 30% ablation. This is the intended trade, and
    reviewer capacity is an open stakeholder variable — the lever is the thresholds and the queue
    policy, not silently ranking people out.
14. **Full historical assessment-version browsing is not implemented (V2).** The current assessment
    plus version metadata is stored; prior assessment snapshots are not. There is likewise no
    AI-check history table — AI results are ephemeral by design.
